2. Purpose and Data Principle

This document defines the IAM data backbone for V1 validation. Developer and Cursor should use it to build database tables, import mapping, validation, source tracking, confidence logic, workflow input snapshots, and archive/history support.

IAM separates source-system fields from IAM standard data domains.

Source system affects mapping confidence, freshness, and evidence strength, not the core IAM workflow rules.

Blank or missing data must not be treated as zero unless it is explicitly confirmed that no record exists.

Weak or partial data should affect confidence, suppression, and review posture rather than creating false precision.

The validation-stage build should proceed using supportable mapped data and should not stall waiting for perfect final Keystroke/AIMS source closure.

3. Locked Hard Rules

IAM is the inventory action engine. It does not replace RSE, IFM, or the broader Decision OS framework.

IAM V1 is a validation-stage build, not a final enterprise version.

One company per workspace/environment in V1.

Priority weights are fixed in V1.

Cash impact leads by default; service/operational risk can override only when clearly more dangerous.

New priorities and holdovers rank separately.

Top 2 remain the core weekly surfaced priorities.

Rejected top priorities do not auto-replace with lower-ranked items in the same cycle and the week may end with zero approved top priorities.

Management may elevate additional items, and materially important out-of-cycle events may create a 3rd top priority.

Management-priority items can remain active outside the normal top-2 cycle.

Grouped actions require one business decision case, one owner, and one action type.

Grouped actions are handled inside Action Detail View in V1.

Completed and archived actions never reopen; similar later issues become new actions with new IDs.

Management-only notes are protected and restricted content must not appear in ordinary non-management views or ordinary exports.

Build should not stall waiting for perfect Keystroke / AIMS mapping. Final source mapping remains a separate addendum.

Any file intended for Keystroke upload or re-import must be tab-delimited and end in .txt.

CSV/XLSX may be used for review, mapping, QA, internal analysis, or customer review, but not as Keystroke import-ready files.

9. Confirmed-None-Exist and Source-of-Truth Rules

Blank data is not zero unless it is explicitly confirmed that no record exists.

Confirmed-none-exist behavior should preserve who confirmed it, when it was confirmed, and the confidence level of that confirmation where practical.

If two mapped sources conflict, flag the conflict, reduce confidence, preserve source lineage, and require a source-of-truth selection or documented reviewer treatment.

Manual assumptions should be visible as manual assumptions and should not masquerade as high-confidence imported data.
