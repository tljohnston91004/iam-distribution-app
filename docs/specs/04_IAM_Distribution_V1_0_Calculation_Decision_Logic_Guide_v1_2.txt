2. Purpose and Core Decision Principle

This document defines the calculation, ranking, workflow, grouped-action, confidence, completion, archive, and visibility rules IAM uses after source data has been mapped into IAM domains.

IAM is not only a scoring product. It is a prioritization-plus-workflow-discipline product.

The ranking engine exists to support a weekly management action model, not a passive exception list.

Workflow state, visibility treatment, confidence posture, and archive behavior are part of IAM decision logic, not side features.

Source-system differences should affect confidence, freshness, and supportability, not the core IAM action logic itself.

3. Locked Hard Rules

IAM is the inventory action engine. It does not replace RSE, IFM, or the broader Decision OS framework.

IAM V1 is a validation-stage build, not a final enterprise version.

One company per workspace/environment in V1.

Priority weights are fixed in V1.

Cash impact leads by default; service/operational risk can override only when clearly more dangerous.

New priorities and holdovers rank separately.

Top 2 remain the core weekly surfaced priorities.

Rejected top priorities do not auto-replace with lower-ranked items in the same cycle and the week may end with zero approved top priorities.

Management may elevate additional items, and materially important out-of-cycle events may create a 3rd top priority.

Management-priority items can remain active outside the normal top-2 cycle.

Grouped actions require one business decision case, one owner, and one action type.

Grouped actions are handled inside Action Detail View in V1.

Completed and archived actions never reopen; similar later issues become new actions with new IDs.

Management-only notes are protected and restricted content must not appear in ordinary non-management views or ordinary exports.

Build should not stall waiting for perfect Keystroke / AIMS mapping. Final source mapping remains a separate addendum.

Any file intended for Keystroke upload or re-import must be tab-delimited and end in .txt.

CSV/XLSX may be used for review, mapping, QA, internal analysis, or customer review, but not as Keystroke import-ready files.

4. Core Decision Flow

Take inventory and evidence snapshot for the review cycle.

Validate minimum support, freshness, and confidence posture.

Identify action candidates from mapped evidence and business context.

Classify evidence strength and confidence level.

Rank new-priority candidates using cash-led logic with the approved override rule.

Separate new priorities from holdovers.

Surface the top 2 featured priorities.

Allow management approval, rejection, and assignment in the same cycle.

Require owner and due/review date before leaving featured status.

Move unresolved work into holdover automatically.

Manage grouped actions conservatively inside Action Detail View.

Approve completion rather than auto-completing from status percentage alone.

Show completed briefly, then archive as useful history.

Preserve never-reopen rule and create new action IDs for later similar issues.

9. Grouped-Action Logic

Grouped actions should be treated conservatively in V1.

Only use grouped actions when multiple child items truly belong to one business decision case.

Grouped actions require one owner and one action type.

Grouped actions stay inside Action Detail View; no separate grouped-action screen in V1.

Child-level overengineering should be avoided in V1.

Partial child resolution should remain visible.

The grouped action remains open until all child items are resolved or formally removed.

Grouping should not be used merely to hide complexity or to compress unrelated issues into one action.

11. Visibility and Protected-Note Logic

Role-based visibility is part of IAM product behavior, not an optional side feature.

Management-only notes are a protected visibility class.

Restricted content must not appear in ordinary non-management views.

Restricted content must not appear in ordinary non-management exports.

Access removal ends live access but should preserve appropriate historical records where allowed.

13. Execution Boundary

IAM does not become RSE settings write-back logic.

IAM does not become IFM funding-allocation logic.

IAM does not become a PO execution system.

IAM does not become a full enterprise workflow platform in V1.

IAM should preserve validation-stage simplicity while still enforcing its hard workflow rules.

15. Playbook Routing and Selection Logic

After a priority or holdover issue is surfaced, IAM should be able to recommend or assign an appropriate Inventory Cash Recovery Action Playbook when trapped-cash/excess inventory is present.

Playbook selection should consider demand credibility, margin preservation value, vendor recovery availability, transfer practicality, item distress level, cash pressure, risk, and RSE correction status.

Before recommending markdown, liquidation, or write-off for overstock inventory, IAM should evaluate Normal Sell-Through / Controlled Runoff.

Playbook routing must remain cause-based and should not blur IAM into RSE, IFM, pricing, or accounting execution logic.

Follow-Up Measurement should be required after any material cash-recovery action.
