7. Major Refresh Areas

7.1 Validation-stage build boundary

State clearly that IAM is a V1 validation-stage build, not a full enterprise platform, not a highly configurable system, and not a multi-company shared workspace product in V1.

Strengthen one company per workspace/environment, fixed priority weights in V1, minimal functional UI, no overbuilt admin/config layer, no full export-permission customization layer, no separate grouped-action screen, and no IAM write-back settings behavior.

7.2 Product-family boundary

Preserve IAM as the inventory action engine, RSE as the replenishment settings engine, IFM as the inventory funding / capital-discipline engine, and Decision OS as the broader priority framework.

State clearly that IAM does not become RSE, IFM, or a general dashboard/reporting layer without action discipline.

7.3 Priority logic refresh

Reflect that cash impact leads by default.

Reflect that service/operational risk can override only when clearly more dangerous and that the override is high-threshold, not a minor-weight modifier.

Reflect that urgency is not a separate top-level ranking factor and confidence is not a lead ranking factor.

Reflect that new priorities and holdovers rank separately.

Reflect that top 2 are the core weekly surfaced priorities, lower-ranked items do not auto-replace rejected top priorities in the same cycle, management may elevate additional items, and materially important out-of-cycle events may create a 3rd top priority.

7.4 Workflow / state logic refresh

Confirm states: surfaced / featured, approved, rejected for cycle, awaiting acceptance, active, holdover, paused, completed, archived.

Confirm behavior: rejection returns issue to future-cycle evaluation, rejected top priorities do not auto-fill with lower-ranked items, approved items are assigned in same cycle, due/review date is required before leaving featured, unresolved featured items move to holdover automatically, awaiting acceptance supports timeout/escalation visibility, completed items remain visible briefly then archive, completed/archived items never reopen, and similar future issues become new actions with new IDs.

7.5 Grouped-action logic refresh

Reflect grouped actions as conservative.

One business decision case required, one owner, one action type, group-level due/review date, partial child resolution visible, group remains open until all child items are resolved or formally removed.

Grouped actions handled inside Action Detail View, no separate grouped-action screen in V1, avoid child-level overengineering in V1.

7.6 Missing-data / confidence refresh

Reflect use what is supportable, avoid false precision, sufficient / partial / insufficient support logic, required-data-missing can block normal confident surfacing, preferred-data-missing narrows confidence but does not automatically block, unsupported normal logic may be suppressed, important but weakly supported issues may appear in review/exception posture, and weak confidence affects display strength.

7.7 Archive / history refresh

Reflect completed and archived as separate states.

Completed visible once as completed, then archive.

Archive is useful history, not a dead status bucket.

Preserve at least action ID, title/label, action type, owner, first surfaced date, completed date, original estimated impact where available, and actual achieved impact only when easily supportable.

No reopen rule remains absolute in V1.

7.8 Security / visibility refresh

Reflect role-based visibility as required.

Management-only notes are a protected visibility class.

Restricted content must not appear in ordinary non-management views.

Export behavior should follow visibility rules as a practical minimum.

Access removal ends live access but preserves history.

7.9 Data expectation refresh

Reflect the stronger IAM data logic and mapping structure already built.

Minimum strong validation stack: item/SKU ID, description, on-hand quantity, units sold / sales history, gross sales dollars, cost, classification, first purchase date, last receipt date, last receipt quantity, open orders / incoming supply, expected receipt dates, item status / protected logic, vendor / brand / supplier, user / role list.

Stronger enhancement stack: allocated / committed quantity, available quantity, inventory value, department / category / subcategory, item creation / activation date, receipt count / quantity in lookback, backorder quantity, returns / negative movement, pack size / MOQ / case quantity, node/location detail, node role / type, transfer indicators/history.

7.10 UAT / validation alignment refresh

Point directly to the approved UAT workbook logic.

Align to these UAT buckets: new priority surfacing, approval / rejection / assignment, holdover movement, completion / archive behavior, grouped-action behavior, missing-data / low-confidence behavior, role / visibility behavior.
